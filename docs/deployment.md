# Деплой бэкендов

Как собрать и развернуть `mobile.api` и `admin.api` для внутренних тестов.
Хостинг — Timeweb Cloud, сервисы — в Docker-контейнерах.

## Главные правила

- **Никаких адресов, логинов и паролей в репозитории.** Репозиторий публичный.
  Секреты попадают в приложение только через переменные окружения, а в контейнер — через
  секреты хостинга или env-файл, который лежит только на сервере.
- **Контейнер ничего не хранит.** Конфиги, доски и статические файлы монтируются в него
  снаружи, поэтому пересоздание контейнера (например, при обновлении) ничего не теряет.
- **Релиз — это собранный JS.** В контейнер скачивается архив релиза из GitHub,
  устанавливаются зависимости, и сервис запускается.

## Что откуда берётся

| Что | Где лежит | Как попадает в сервис |
|---|---|---|
| Код (`main.js`, `package.json`, `pnpm-lock.yaml`) | архив в GitHub Release | скачивается при сборке образа |
| Секреты (`MONGO_URI`, `AUTH_TOKEN_SECRET`) | секреты хостинга / env-файл на сервере | переменные окружения |
| Конфиг (`*-configuration.json`) | на сервере, в каталоге данных | монтируется, путь — `CONFIG_PATH` |
| Доски (`storages/boards`) | на сервере, в каталоге данных | монтируется, путь — в конфиге |
| Статические файлы (аватары и т.п.) | на сервере, в каталоге данных | монтируется, путь — в конфиге |
| MongoDB | отдельный сервис | адрес и пароль в `MONGO_URI` |

## Переменные окружения

### mobile.api

| Переменная | Обязательна | Описание |
|---|---|---|
| `MONGO_URI` | да | подключение к MongoDB вместе с логином и паролем: `mongodb://user:password@host:27017/?authSource=admin` |
| `AUTH_TOKEN_SECRET` | да | ключ подписи токенов игроков, не меньше 32 символов (`openssl rand -hex 32`). Смена ключа разлогинивает всех игроков (они войдут снова при следующем запросе) |
| `CONFIG_PATH` | да* | путь к конфигу внутри контейнера. *Либо аргумент `--config=<путь>` |
| `PORT` | нет | порт, по умолчанию `3001` |

Без секретов сервис не запустится и назовёт, каких переменных нет. Если секрет оставлен
в конфиге (`dependencies.mongo.uri`, `auth.tokenSecret`), сервис тоже не запустится —
это сделано намеренно, чтобы секрет нельзя было случайно держать в файле.

### admin.api

| Переменная | Обязательна | Описание |
|---|---|---|
| `CONFIG_PATH` | да* | путь к конфигу внутри контейнера. *Либо `--config=<путь>` |
| `PORT` | нет | порт, по умолчанию `3000` |

### Локальная разработка

У каждого бэкенда свой `.env` в папке приложения — те же переменные, что и в контейнере.
Nx подхватывает его сам при `npx nx serve <app>`, в git он не попадает. Шаблоны лежат
рядом и коммитятся:

- [`apps/mobile.api/.env.example`](../apps/mobile.api/.env.example)
- [`apps/admin.api/.env.example`](../apps/admin.api/.env.example)

```bash
cp apps/mobile.api/.env.example apps/mobile.api/.env
```

```bash
cp apps/admin.api/.env.example apps/admin.api/.env
```

Локально `CONFIG_PATH` указывает на `.mount/cfg/...` относительно корня репозитория.

Nx читает `.env` при запуске задачи: после его изменения `nx serve` нужно перезапустить.
Корневой `.env` (если он есть) Nx подмешивает во все задачи, поэтому переменные
приложений в нём держать не нужно.

## Каталог данных на сервере

Всё, что должно пережить пересоздание контейнера, лежит в одном каталоге на сервере.
Его же удобно бэкапить и копировать между окружениями.

```
/srv/dead-lines-inc/
  cfg/
    mobile-api-configuration.json
    admin-api-configuration.json
  storages/
    boards/                 доски (*.json): пишет admin.api, читает mobile.api
  assets/                   статические файлы, которые отдаёт mobile.api
    avatars/
  secrets/
    mobile-api.env          только если секреты передаются файлом; права 600
```

В контейнер каталоги монтируются так:

| На сервере | В контейнере | mobile.api | admin.api |
|---|---|---|---|
| `/srv/dead-lines-inc/cfg` | `/data/cfg` | только чтение | только чтение |
| `/srv/dead-lines-inc/storages` | `/data/storages` | да | да, с записью |
| `/srv/dead-lines-inc/assets` | `/data/assets` | только чтение | — |

Пути внутри конфигов на сервере — абсолютные, в контейнере:

```jsonc
// mobile-api-configuration.json (фрагмент)
{
  "dependencies": {
    "boardProvider": { "storage": { "rootPath": "/data/storages/boards", ... } },
    "mongo": { "database": "deadLinesInc" }
  },
  "assets": { "rootPath": "/data/assets" },
  "cors": { "allowedOrigins": ["https://<адрес веб-версии>"] }
}
```

Отличие от локального конфига (`.mount/cfg`) — только эти пути и `cors`. Остальное
(тексты, пул аватаров, параметры челленджей) берётся из репозитория как есть.

Доски и конфиги переносятся между окружениями простым копированием файлов.

### Статические файлы

`mobile.api` отдаёт файлы из `assets.rootPath` по адресу `/assets/...`. Адреса меняются
вместе с содержимым файла, поэтому клиенты кешируют файлы навсегда. Чтобы добавить или
заменить файл, достаточно положить его в `/srv/dead-lines-inc/assets` и перезапустить
сервис: адреса файлов вычисляются один раз и запоминаются до перезапуска. Новый аватар
к тому же нужно добавить в `avatarPool` конфига.

Когда нагрузка вырастет, файлы можно перенести в S3-хранилище Timeweb или за CDN
и указать в конфиге `assets.publicBaseUrl` — тогда приложение будет брать их оттуда,
а не из API.

## Релиз

Релизы делает [semantic-release](https://semantic-release.gitbook.io/), отдельно для
каждого бэкенда. Версия считается по коммитам ([Conventional Commits](https://www.conventionalcommits.org/))
с прошлого релиза этого приложения:

- `fix: ...` — патч (`1.0.1`), `feat: ...` — минорная версия (`1.1.0`),
  `!` после типа или `BREAKING CHANGE:` в теле коммита — мажорная (`2.0.0`);
- `chore`, `docs`, `refactor` и т.п. релиза не дают;
- учитываются только коммиты, которые меняли само приложение или workspace-библиотеки,
  от которых оно зависит (по графу Nx). Коммит только в `apps/mobile` релиза бэкендов не
  вызовет, коммит в `libs/common/models` — вызовет у обоих.

Что делает релиз приложения:

1. Считает версию и пишет заметки к релизу.
2. Собирает приложение и упаковывает в архив
   ([`tools/release/pack-backend.mjs`](../tools/release/pack-backend.mjs)); версия
   записывается в `package.json` архива.
3. Ставит тег `<приложение>-v<версия>`, например `mobile.api-v1.2.0`.
4. Создаёт GitHub Release с заметками и архивом `mobile.api-v1.2.0.tar.gz`.

В репозиторий ничего не коммитится, в npm ничего не публикуется. Первый релиз
приложения — `1.0.0`.

Настройки: общая часть — [`tools/release/backend-release-config.mjs`](../tools/release/backend-release-config.mjs),
у приложения — `apps/<приложение>/release.config.mjs`.

### Как выпустить

Релиз делается с ветки `main`, запушенной в GitHub: semantic-release проверяет, что
локальная ветка совпадает с удалённой, и пушит тег.

Нужен токен GitHub с правом `contents: write` на репозиторий — в переменной `GITHUB_TOKEN`
(или `GH_TOKEN`). Токен в файлы не кладётся. Если `gh` залогинен, можно взять его токен.

Сначала посмотреть, что будет, ничего не меняя:

```bash
GITHUB_TOKEN=$(gh auth token) npx nx run mobile.api:release --dry-run
```

Выпустить:

```bash
GITHUB_TOKEN=$(gh auth token) npx nx run mobile.api:release
```

Для admin.api — то же с `admin.api:release`.

### Архив релиза

- `main.js` — весь код сервиса, включая библиотеки `@dead-lines-inc/*`;
- `package.json` — версия релиза и внешние зависимости с точными версиями;
- `pnpm-lock.yaml` — урезанный lockfile под эти зависимости;
- `main.js.map` — для читаемых стектрейсов.

Ни секретов, ни конфигов в архиве нет. Репозиторий публичный, поэтому архив скачивается
без токена:

```
https://github.com/wallride/froggo/releases/download/mobile.api-v1.0.0/mobile.api-v1.0.0.tar.gz
```

## Сборка и запуск контейнера

Схема одинакова для обоих сервисов (Node.js 24, как в `engines` корневого `package.json`):

1. Скачать архив релиза и распаковать в рабочий каталог, например `/app`.
2. Установить зависимости строго по lockfile:
   ```bash
   npm install -g pnpm@11
   ```
   ```bash
   pnpm install --prod --frozen-lockfile
   ```
3. Запустить с секретами в окружении и смонтированным `/data`:
   ```bash
   node main.js
   ```
   с `CONFIG_PATH=/data/cfg/mobile-api-configuration.json`.

Образ не зависит от окружения: всё, что отличается между окружениями, приходит через
`/data` и переменные окружения. Обновление — новый образ с новой версией релиза и
пересоздание контейнера; данные остаются на месте.

## Timeweb

Требование «данные монтируются снаружи» лучше всего выполняется на **облачном сервере
(VPS) с Docker**: каталог `/srv/dead-lines-inc` на диске сервера монтируется в контейнеры.
Платформа приложений Timeweb (Apps) проще в обслуживании, но перед выбором стоит проверить,
даёт ли она постоянные тома — без них доски и статика будут теряться при пересоздании.

### MongoDB

- **Управляемая база Timeweb** — бэкапы и обновления на стороне хостинга. Доступ
  ограничить приватной сетью с сервером.
- **Или контейнер на том же VPS** — со своим томом для данных и без открытого наружу
  порта.

В обоих случаях адрес и пароль — только в `MONGO_URI`. Для приложения стоит завести
отдельного пользователя с правами только на базу `deadLinesInc`, а не использовать админа.

### Сеть

- **mobile.api** — наружу через обратный прокси с HTTPS (например, Caddy: сертификат
  получает сам).
- **admin.api** — **не открывать в интернет**: в нём нет аутентификации. Пусть слушает
  только локальный адрес сервера, а заходить в него через SSH-туннель:
  ```bash
  ssh -L 3000:localhost:3000 user@<сервер>
  ```

### Клиенты

- **Мобильное приложение**: адрес API вшивается при сборке через `EXPO_PUBLIC_API_BASE_URL`
  (переменная окружения EAS Build). Это не секрет — адрес всё равно виден в приложении.
- **Админка** (если её разворачивать): `VITE_API_BASE_URL` при сборке.

## Бэкапы

- Каталог `/srv/dead-lines-inc` целиком (кроме `secrets/`, их бэкапить отдельно и
  безопасно).
- MongoDB — `mongodump` по расписанию, либо бэкапы управляемой базы.
