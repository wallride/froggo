# Деплой бэкендов

Как собрать и развернуть `mobile.api` и `admin.api` для внутренних тестов.
Хостинг — Timeweb Cloud, сервисы — в Docker-контейнерах.

## Главные правила

- **Никаких адресов, логинов и паролей в репозитории.** Репозиторий публичный.
  Секреты попадают в приложение только через переменные окружения, а в контейнер — через
  секреты хостинга или env-файл, который лежит только на сервере.
- **Контейнер ничего не хранит.** Конфиги и статические файлы монтируются в него
  снаружи, доски и остальные данные — в MongoDB, поэтому пересоздание контейнера
  (например, при обновлении) ничего не теряет.
- **Релиз — это собранный JS.** В контейнер скачивается архив релиза из GitHub,
  устанавливаются зависимости, и сервис запускается.

## Что откуда берётся

| Что | Где лежит | Как попадает в сервис |
|---|---|---|
| Код (`main.js`, `package.json`, `pnpm-lock.yaml`) | архив в GitHub Release | скачивается при сборке образа |
| Секреты (`MONGO_URI`, `AUTH_TOKEN_SECRET`) | секреты хостинга / env-файл на сервере | переменные окружения |
| Конфиг (`configuration.json`) | в архиве релиза | читается рядом с `main.js`, путь можно переопределить `CONFIG_PATH` |
| Доски | MongoDB, коллекция `boards` | адрес и пароль в `MONGO_URI`; пишет admin.api, читает mobile.api |
| Статические файлы (аватары и т.п.) | в архиве релиза (`assets/` рядом с `main.js`) | ничего не монтируется |
| MongoDB | отдельный сервис | адрес и пароль в `MONGO_URI` |

## Переменные окружения

### mobile.api

| Переменная | Обязательна | Описание |
|---|---|---|
| `MONGO_URI` | да | подключение к MongoDB вместе с логином и паролем: `mongodb://user:password@host:27017/?authSource=admin` |
| `AUTH_TOKEN_SECRET` | да | ключ подписи токенов игроков, не меньше 32 символов (`openssl rand -hex 32`). Смена ключа разлогинивает всех игроков (они войдут снова при следующем запросе) |
| `MINIMUM_APP_VERSION` | да | минимальная версия приложения (`x.y.z`). Сборки ниже, как и запросы без версии, получают `426` и показывают экран обновления |
| `PORT` | нет | порт, по умолчанию `3001` |
| `CORS_ALLOWED_ORIGINS` | нет | origin'ы веб-версии через запятую (`https://a,https://b`). Не задана — разрешены любые (годится локально, в продакшене задайте) |
| `ASSETS_ROOT_PATH` | нет | где лежат файлы ассетов. По умолчанию `assets` рядом с `main.js` — так они лежат в архиве релиза |
| `ASSETS_PUBLIC_BASE_URL` | нет | адрес CDN/прокси для ассетов (`https://cdn.example.com/assets`). Не задан — файлы отдаёт сам API |
| `CONFIG_PATH` | нет | переопределяет контентный конфиг; по умолчанию `configuration.json` рядом с `main.js` |

Без обязательных переменных сервис не запустится и назовёт, каких не хватает. Если секрет
или env-значение оставлены в конфиге (`dependencies.mongo.uri`, `auth.tokenSecret`,
`minimumAppVersion`), сервис тоже не запустится — это сделано намеренно, чтобы секрет
нельзя было случайно держать в файле.

### admin.api

| Переменная | Обязательна | Описание |
|---|---|---|
| `MONGO_URI` | да | подключение к MongoDB; та же база, что у mobile.api — админка пишет доски, которые читает игра |
| `PORT` | нет | порт, по умолчанию `3000` |
| `CONFIG_PATH` | нет | переопределяет контентный конфиг; по умолчанию `configuration.json` рядом с `main.js` |

### Локальная разработка

У каждого бэкенда свой `.env` в папке приложения — те же переменные, что и в контейнере.
Nx подхватывает его сам при `npx nx serve <app>`, в git он не попадает. Шаблоны лежат
рядом и коммитятся:

- [`apps/mobile.api/.env.example`](../apps/mobile.api/.env.example)
- [`apps/admin.api/.env.example`](../apps/admin.api/.env.example)

```bash
cp apps/mobile.api/.env.example apps/mobile.api/.env
```

```bash
cp apps/admin.api/.env.example apps/admin.api/.env
```

Локально `CONFIG_PATH` указывает на `.mount/cfg/...` относительно корня репозитория.

Nx читает `.env` при запуске задачи: после его изменения `nx serve` нужно перезапустить.
Корневой `.env` (если он есть) Nx подмешивает во все задачи, поэтому переменные
приложений в нём держать не нужно.

## Что где лежит при деплое

Контейнер ничего не монтирует: всё, что нужно для старта, либо в архиве релиза, либо в env.

```
архив релиза (распакован в /app)
  main.js, package.json, pnpm-lock.yaml
  configuration.json        контентный конфиг (тексты, лимиты, пул аватаров) — одинаковый везде
  assets/avatars/*.png      файлы аватаров
env контейнера
  MONGO_URI, AUTH_TOKEN_SECRET, MINIMUM_APP_VERSION, PORT, CORS_ALLOWED_ORIGINS
```

Поэтому на сервере не нужен каталог данных: доски — в MongoDB, конфиг и аватары — в образе.
Архив собирает `tools/release/pack-backend.mjs` из `.mount/cfg/*-configuration.json` и
(для mobile.api) `.mount/assets`, так что правка текстов или новый аватар — это коммит,
релиз и новое развёртывание, а не правка файла на сервере.

Пути внутри конфига — только относительные имена коллекций; всё, что зависит от окружения,
приходит из env (см. выше):

```jsonc
// configuration.json (фрагмент)
{
  "dependencies": {
    "boardProvider": { "collectionName": "boards" },
    "mongo": { "database": "deadLinesInc" }
  }
}
```

`MINIMUM_APP_VERSION` — минимальная версия мобильного приложения, которую пускает API.
Поднимайте её вместе с выкладкой новой версии приложения в сторы: сборки ниже получат `426`
и покажут экран обновления. Это env, а не конфиг: менять её можно без пересборки релиза.

Локально ничего этого нет: `apps/<app>/.env` указывает `CONFIG_PATH` на `.mount/cfg/...`,
а `ASSETS_ROOT_PATH` — на `.mount/assets`.

Данные переносятся между окружениями через MongoDB (`mongodump`/`mongorestore`). Если доски
ещё лежат файлами, их разово импортирует `tools/migrate-boards-to-mongo.mjs`: он идемпотентно
раскладывает `*.json` по коллекции `boards`, поддерживает `--dry-run` и берёт адрес базы
из `MONGO_URI`.

### Статические файлы

`mobile.api` отдаёт файлы из `ASSETS_ROOT_PATH` (по умолчанию `assets` рядом с `main.js`)
по адресу `/assets/...`. Адреса меняются вместе с содержимым файла, поэтому клиенты кешируют
файлы навсегда. Файлы запекаются в релиз: чтобы добавить или заменить аватар, положите его
в `.mount/assets/avatars`, добавьте id в `avatarPool` конфига и выпустите релиз — сервис
подхватит новое содержимое при развёртывании.

Когда нагрузка вырастет, файлы можно перенести в S3-хранилище Timeweb или за CDN
и указать `ASSETS_PUBLIC_BASE_URL` — тогда приложение будет брать их оттуда, а не из API.

## Релиз

Релизы делает [semantic-release](https://semantic-release.gitbook.io/), отдельно для
каждого бэкенда. Версия считается по коммитам ([Conventional Commits](https://www.conventionalcommits.org/))
с прошлого релиза этого приложения:

- `fix: ...` — патч (`1.0.1`), `feat: ...` — минорная версия (`1.1.0`),
  `!` после типа или `BREAKING CHANGE:` в теле коммита — мажорная (`2.0.0`);
- `chore`, `docs`, `refactor` и т.п. релиза не дают;
- учитываются только коммиты, которые меняли само приложение или workspace-библиотеки,
  от которых оно зависит (по графу Nx). Коммит только в `apps/mobile` релиза бэкендов не
  вызовет, коммит в `libs/common/models` — вызовет у обоих.

Что делает релиз приложения:

1. **До** создания тега проверяет доступ к GitHub: `gh` установлен, авторизация рабочая,
   репозиторий виден с правом `contents: write`. Если проверка не прошла, тег не создаётся.
2. Считает версию и пишет заметки к релизу.
3. Собирает приложение и упаковывает в архив
   ([`tools/release/pack-backend.mjs`](../tools/release/pack-backend.mjs)); версия
   записывается в `package.json` архива.
4. Ставит тег `<приложение>-v<версия>`, например `mobile.api-v1.2.0`.
5. Создаёт GitHub Release с заметками и архивом `mobile.api-v1.2.0.tar.gz`
   ([`tools/release/publish-backend.mjs`](../tools/release/publish-backend.mjs) через
   [`gh-release.mjs`](../tools/release/gh-release.mjs), без `@semantic-release/github`).

В репозиторий ничего не коммитится, в npm ничего не публикуется. Первый релиз
приложения — `1.0.0`.

Настройки приложения — `apps/<приложение>/.releaserc.json`: цель Nx `release` запускает
semantic-release в папке приложения (`cwd: {projectRoot}`), и он сам читает конфиг оттуда
(общего конфига в `tools/` больше нет). Код шагов релиза — [`tools/release/*.mjs`](../tools/release).
Пошаговая инструкция — [release.md](release.md).

### Как выпустить

Релиз делается с ветки `main`, запушенной в GitHub: semantic-release проверяет, что
локальная ветка совпадает с удалённой, и пушит тег.

Нужен токен GitHub с правом `contents: write` на репозиторий — в переменной `GH_TOKEN`
(подходит и `GITHUB_TOKEN`; `GH_TOKEN` главнее, его и использует `gh`). Токен в файлы
не кладётся. Если `gh` залогинен, можно взять его токен.

Проверка перед релизом смотрит на доступ к репозиторию, а не на `gh auth status`: тот
возвращает ошибку, если в связке ключей завалялся недействительный аккаунт, даже когда
рабочий токен из `GH_TOKEN` в порядке. Убрать такой аккаунт: `gh auth logout -h github.com -u <логин>`.

Сначала посмотреть, что будет, ничего не меняя:

```bash
GH_TOKEN=$(gh auth token) npx nx run mobile.api:release --dry-run
```

Выпустить:

```bash
GH_TOKEN=$(gh auth token) npx nx run mobile.api:release
```

Для admin.api — то же с `admin.api:release`.

Проверить, что токен живой, можно заранее: `gh auth status` (или `gh auth login -h github.com`,
если он просит перелогиниться).

### Если релиз прервался

semantic-release ставит и пушит тег **до** публикации релиза — так устроено его ядро.
Поэтому любой сбой на этапе создания GitHub Release оставляет тег без релиза, а повторный
запуск ничего не делает: новых коммитов после тега нет, значит нет и «следующего релиза».

Публикация сделана идемпотентной, чтобы это лечилось:

- если релиза для тега ещё нет — он создаётся с `--verify-tag` (то есть только по
  существующему тегу);
- если релиз уже есть — он обновляется (`gh release edit --draft=false`), а архив
  перезаливается с `--clobber`;
- заметки берутся из того же расчёта semantic-release, так что повтор даёт тот же результат.

Обычно достаточно починить доступ к GitHub и запустить релиз ещё раз — версия будет той же,
а релиз досоздастся. Если перезапускать semantic-release не хочется (например, он не видит
незавершённый релиз), есть отдельный скрипт:

```bash
node tools/release/repair-release.mjs mobile.api            # последний тег
node tools/release/repair-release.mjs mobile.api 1.0.0      # конкретная версия
node tools/release/repair-release.mjs mobile.api --dry-run  # только показать план
node tools/release/repair-release.mjs mobile.api --force    # перезаписать существующий релиз
```

Скрипт находит тег `<приложение>-v<версия>`, собирает заметки по коммитам между предыдущим
тегом и этим (по тем же корням проекта, что и обычный релиз), проверяет доступ к GitHub,
берёт архив из `dist/release` или собирает его из помеченного коммита и публикует релиз.
Если HEAD не совпадает с тегом и архива нет, скрипт остановится: публиковать код из-под
другого коммита нельзя.

Через Nx то же самое: `npx nx run mobile.api:repair-release` (`admin.api:repair-release`).

### Архив релиза

- `main.js` — весь код сервиса, включая библиотеки `@dead-lines-inc/*`;
- `package.json` — версия релиза и внешние зависимости с точными версиями;
- `pnpm-lock.yaml` — урезанный lockfile под эти зависимости;
- `main.js.map` — для читаемых стектрейсов;
- `configuration.json` — контентный конфиг (`.mount/cfg/<app>-configuration.json`);
- `assets/` — файлы аватаров (только mobile.api, из `.mount/assets`).

Секретов в архиве нет: они приходят только через env. Конфиг и ассеты — часть релиза,
поэтому контейнер стартует без монтирований. Репозиторий публичный, архив скачивается
без токена:

```
https://github.com/wallride/froggo/releases/download/mobile.api-v1.0.0/mobile.api-v1.0.0.tar.gz
```

## Сборка и запуск контейнера

Схема одинакова для обоих сервисов (Node.js 24, как в `engines` корневого `package.json`):

1. Скачать архив релиза и распаковать в рабочий каталог, например `/app`.
2. Установить зависимости строго по lockfile:
   ```bash
   npm install -g pnpm@11
   ```
   ```bash
   pnpm install --prod --frozen-lockfile
   ```
3. Запустить с секретами и переключателями в окружении:
   ```bash
   MONGO_URI=... AUTH_TOKEN_SECRET=... MINIMUM_APP_VERSION=1.0.0 node main.js
   ```

Образ не зависит от окружения: всё, что отличается между окружениями, приходит через env
(`config.json` рядом с `main.js` одинаков везде). Живость — `GET /api/health`: хостинг
может проверять её до открытия трафика, БД и версия приложения ей не мешают. Обновление —
новый образ с новой версией релиза и пересоздание контейнера; данные остаются в MongoDB.

## Docker-образ

В корне репозитория лежит `Dockerfile` для `mobile.api` (сборка в два этапа):

```bash
docker build -t mobile-api .
docker run -d --name=mobile-api -p 3000:3000 -e MONGO_URI=$MONGO_URI -e AUTH_TOKEN_SECRET=$AUTH_TOKEN_SECRET -e MINIMUM_APP_VERSION=1.0.0 mobile-api
```

- **build**: `pnpm install --frozen-lockfile`, затем `nx run mobile.api:build`. Webpack
  кладёт в `dist/apps/mobile.api` бандл и `package.json` с точными версиями внешних
  зависимостей; по нему в отдельном каталоге вне workspace строится production-lockfile.
- **runtime**: `node:24.11.1-alpine`, `pnpm install --prod --frozen-lockfile`, затем
  `main.js`, `configuration.json` и `assets/` из `.mount` — тот же набор, что кладёт в
  архив `tools/release/pack-backend.mjs`. Порог 3000 закреплён через `EXPOSE`
  (без него прокси платформы ждёт 8080), живость — `HEALTHCHECK` на `GET /api/health`.
- **`.dockerignore`** не пускает в образ `node_modules`, `dist`, `.nx`, `.git` и локальные
  `.env`.

Переменные из `apps/mobile.api/.env` нужны только для запуска из репозитория: `CONFIG_PATH`
и `ASSETS_ROOT_PATH` указывают на `.mount`, а в образе конфиг и ассеты уже лежат рядом с
`main.js`. Поэтому при `docker run --env-file apps/mobile.api/.env` эти две строки нужно
убрать, иначе контейнер будет искать файлы, которых в нём нет.

### Отладка «запросы не доходят»

Приложение отвечает живостью на трёх путях — `/`, `/health` и `/api/health`
(`{status, database, uptime, startedAt}`), так что проба платформы проходит независимо от
того, какой путь у неё настроен: любой из них возвращает `200`, даже если база недоступна
(`database: "disconnected"`). `uptime` показывает, не перезапускался ли контейнер между
проверками.

Важное следствие: **порт открывается сразу, не дожидаясь MongoDB**. Подключение и создание
индексов идут в фоне (`Database` в логах), иначе недостижимый `MONGO_URI` держал бы порт
закрытым, а проба провайдера падала бы без единой подсказки. Цена: пока база не поднялась,
маршруты, которым она нужна, отвечают `500`, а `health` продолжает быть `200`.

Логи контейнера делятся на два вида:

- `[Bootstrap]` — при старте: конфигурация без секретов, фактический адрес и порт
  (`listening on 0.0.0.0:3000 (PORT=…)`), hostname и IPv4 контейнера. Если здесь `PORT`
  отличается от `EXPOSE` в образе, прокси платформы и приложение слушают разные порты.
- `[Database]` — `connecting to …`, `ready: … (55ms)` или `not ready after 30007ms: … — connect
  ECONNREFUSED …`: видно и адрес (без креденшелов), и время, и причину.
- `[HTTP]` — каждая строка это один запрос: `GET /api/health → 200 3ms completed
  ip=… forwarded=… proto=… host=… ua=…`. Логируются и `404`, и запросы, не получившие
  ответа (`aborted` — например, база не ответила).

Как читать результат:

| Что видно в логах | Что это значит |
|---|---|
| нет ни одной строки `[HTTP]` | трафик до процесса не доходит: маршрут домена, сертификат или порт — на стороне платформы |
| есть `[HTTP]` с `200` от пробника платформы | приложение живое, домен просто ещё не раздаётся наружу |
| есть `[HTTP] … → 404` | проба приходит на путь, которого нет: смотреть путь healthcheck в панели |
| есть `[HTTP] … aborted` | запрос пришёл, но ответа не получил |
| `[Database] not ready … ECONNREFUSED` | база недоступна из контейнера: `MONGO_URI` указывает на localhost, приватный адрес не тот или IP платформы не в белом списке |

`x-forwarded-for` и `x-forwarded-proto` в строке показывают, что именно присылает прокси
платформы, — по ним видно, пришёл запрос через прокси или напрямую изнутри сети.

## Timeweb

Приложение уже устроено так, что ему не нужны постоянные диски: доски — в MongoDB,
конфиг и аватары — в образе, остальное — env. Поэтому подходит и **облачный сервер (VPS)
с Docker**, и **Платформа приложений Timeweb (Apps)**, у которой монтирований нет вообще.
Для App Platform: сборка образа из репозитория (или пуша в их реестр), `EXPOSE` в
Dockerfile, healthcheck — `GET /api/health` (ждёт 2xx), переменные окружения — в панели.

### MongoDB

- **Управляемая база Timeweb** — бэкапы и обновления на стороне хостинга. Доступ
  ограничить приватной сетью с сервером.
- **Или контейнер на том же VPS** — со своим томом для данных и без открытого наружу
  порта.

В обоих случаях адрес и пароль — только в `MONGO_URI`. Для приложения стоит завести
отдельного пользователя с правами только на базу `deadLinesInc`, а не использовать админа.

### Сеть

- **mobile.api** — наружу через обратный прокси с HTTPS (например, Caddy: сертификат
  получает сам).
- **admin.api** — **не открывать в интернет**: в нём нет аутентификации. Пусть слушает
  только локальный адрес сервера, а заходить в него через SSH-туннель:
  ```bash
  ssh -L 3000:localhost:3000 user@<сервер>
  ```

### Клиенты

- **Мобильное приложение**: адрес API вшивается при сборке через `EXPO_PUBLIC_API_BASE_URL`
  (переменная окружения EAS Build). Это не секрет — адрес всё равно виден в приложении.
- **Админка** (если её разворачивать): `VITE_API_BASE_URL` при сборке.

## Бэкапы

- Конфиг и ассеты бэкапить не нужно — они восстанавливаются из релиза (архив на GitHub).
- MongoDB — `mongodump` по расписанию, либо бэкапы управляемой базы.
